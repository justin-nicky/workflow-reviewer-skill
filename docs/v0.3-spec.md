# workflow-reviewer v0.3 — spec

Status: draft, not started. v0.2.x ships first (see "Prerequisites").
Owner: @justin-nicky

## 1. Why v0.3

v0.2 reads each coding tool's own session files (transcripts) and maps them with declarative adapters. Real use in v0.2 showed three structural problems:

1. **Maintenance.** Transcript formats are private and undocumented, and change without notice. In two weeks of testing: Codex 0.171 added a record type that paused reviews; Codex's running token total lags behind a live turn, which failed a cross-check; Cursor changed how it links subagents, which hid most of a task's work. Every host release can silently break any of about a dozen mapped fields.
2. **Cost and independence of in-session review.** The review runs inside the session it reviews, so every review step re-reads the whole session context. One review cost about 4x the task it reviewed. The agent also grades its own work, and in one run tried to delete a failing check to get past it.
3. **One task gives weak signal.** Short tasks return "no changes". The questions users care about most, such as which skills are never used or which waste keeps recurring, need many sessions.

v0.3 moves the main data source from reverse-engineered transcripts to the tools' documented hook systems, adds cross-session review, and puts release and drift management on a footing one maintainer can sustain.

## 2. Goals

- G1. Turns, tool calls, commands, errors, subagents and timing come from a recorder we own, fed by documented hooks, in one stable event format across tools.
- G2. Transcripts are read only for what hooks don't provide (token usage) and as a fallback for unrecorded sessions.
- G3. Recording is off by default, opt-in per task or per project, and never committed to a shared repository.
- G4. Cross-session review: "review my last N sessions" in a fresh, cheap session, independent of the work it reviews.
- G5. Format drift degrades to a visible warning, never to a pause or silently wrong numbers.
- G6. Releases reach users through each tool's normal update path, and the report tells users when updating would help.

## 3. Non-goals

- Cloud agents (Cursor cloud, cloud Devin): no local hooks or files. Degraded mode as today.
- Pricing or cost estimates. Tokens only, as in v0.2.
- Automatic adapter building during a review. It becomes a manual contributor command (§9).
- Any network access by the script. The update nudge (§10) and drift checks (§11) work offline or run on the maintainer's side.

## 4. Prerequisites (v0.2.x, before any v0.3 work)

- Freeze the review window at the invocation; never read records after it.
- Second counts (cross-checks) compare values for the reviewed window only.
- Unknown record types and failed cross-checks are warnings shown in the report. Pause only when a core metric is clearly absent (e.g. no token records at all on a tool that records tokens).
- An adapter may add mappings but never remove or loosen a check (`--save-adapter` enforces it).
- Devin and Cline labelled experimental.
- One-click issue link with safe diagnostics (§11).

## 5. Architecture

```
coding tool (Claude Code / Codex / Cursor)
   │ documented hook events (JSON on stdin)
   ▼
scripts/record_event.py   ← one script, all tools; stdlib only
   │ normalised event lines (our schema, §6)
   ▼
~/.local/state/workflow-reviewer/sessions/<host>/<session_id>.jsonl
   │
   ▼
transcript_metrics.py  ← source ladder:
   1. recorder log (turns, tools, commands, errors, subagents, timing)
   2. tool transcript (token usage only; full fallback when no recording)
   │
   ▼
health table → report (single task or cross-session)
```

### Source ladder rules

- If a recorder log covers the window, it is the source for every metric it carries. The report says "recorded".
- Token usage always comes from the transcript (hooks don't carry it). If the token mapping fails, tokens are "not measurable" and everything else stays exact.
- With no recording, v0.2 behaviour applies (transcript adapters), labelled "from transcript".
- Where both exist, the recorder log and the transcript are cross-checked on turns and tool calls (a free second count). A mismatch is a warning, never a pause.

## 6. Recorder event schema (v1)

One JSON object per line. Unknown fields are ignored by readers; fields are only ever added.

| Field | Type | Notes |
|---|---|---|
| `v` | int | Schema version, starts at 1 |
| `ts` | string | ISO 8601 UTC, written by the recorder (not the tool) |
| `host` | string | `claude-code`, `codex`, `cursor` |
| `host_version` | string or null | When the payload or environment provides it |
| `session` | string | The tool's session id; subagents carry their own plus `parent_session` |
| `event` | string | `session_start`, `prompt`, `tool_end`, `subagent_start`, `subagent_stop`, `stop`, `compact`, `interrupt` |
| `tool` | string or null | Tool name as the host reports it |
| `category` | string or null | `read`, `edit`, `shell`, `search`, `agent`, `skill`, `other` |
| `cmd0` | string or null | First word of a shell command only (e.g. `pytest`), plus `verify: true` when it matches the verify pattern |
| `ok` | bool or null | Tool success, from exit code where available |
| `exit_code` | int or null | |
| `duration_ms` | int or null | When the host provides it or both ends are observed |
| `skill` | string or null | Skill name when a skill is invoked |
| `prompt_len` | int or null | Length only; never the prompt text |

Never recorded: prompt text, tool inputs beyond `cmd0`, tool outputs, file contents, file paths, environment values. Each host's mapping from hook payload to this schema is a small declarative table, tested against a captured payload fixture per host and event.

## 7. Recording control

- `transcript_metrics.py --record on [--for 2h] [--project]`, `--record off`, `--record status`.
- Default after setup: off. When off, the recorder exits immediately (target: under 20 ms per event).
- State lives in `~/.config/workflow-reviewer/record.json` (global) or `.workflow-reviewer/record.json` in the project (git-ignored).
- Retention: logs older than 14 days are deleted on the next recorder run (configurable). `--record purge` deletes all logs.
- The report states whether the window was recorded and, if not, says how to turn recording on next time.

## 8. Distribution

| Route | Contents | Hooks | Update path |
|---|---|---|---|
| Claude Code plugin | skill + `hooks/hooks.json` + recorder | Wired by the plugin | Marketplace update; `version` in `plugin.json` must be bumped every release |
| Codex plugin | skill + hooks + recorder | Wired by the plugin; user trusts hooks once | `codex plugin marketplace upgrade` |
| Cursor plugin (`.cursor-plugin`) | skill + hooks + recorder | Wired by the plugin | Automatic after marketplace review |
| Agent Plugins (standard) | skill only | None (standard has no hooks) | Per client |
| Skills CLI | skill only | `--setup-hooks` (opt-in, shows the exact change, `--remove-hooks` to undo) | `npx skills update` |

- Hooks are wired at **local scope** by default: this machine, not written into any committed file. A user-wide option exists for people who want everything recorded. Never project scope in committed settings, which would record collaborators without consent.
- To verify before building: Codex per-project plugin enablement (state appears to live in `~/.codex/config.toml`); the command name each tool shows for a plugin-provided skill (namespacing); hook support and payload fields on Windows.

## 9. Adapter flow (changed)

- No automatic adapter building inside a review. On drift, the review runs with warnings and offers the issue link (§11).
- `--probe` and `--save-adapter` stay as contributor tools, documented in `adding-a-host.md`, and keep the v0.2.3 rule: adapters may add mappings, never remove or loosen checks.

## 10. Cross-session review

- Runs out of session: a fresh agent session or a plain CLI run, so it never re-reads a working session's context.
- `--sessions N` or `--since 7d`, optionally `--project <path>` and `--host <host>`.
- Reads recorder logs first, transcripts as fallback, and states per session which was used.
- Findings it can support:
  - skills installed but never loaded across N sessions (only with N ≥ 10 sessions and a stated window; never from one session)
  - skills that always load together (candidate overlaps), with counts
  - recurring waste: repeated reads of the same file, repeated failing commands, verify runs before the last edit, by count and share of sessions
  - always-on instruction files and their share of context across sessions
- Same findings schema and HTML report, with a sessions table in place of the per-turn breakdown. A new `scope` field in the findings (`task` or `sessions`) is the only schema addition.

## 11. Drift monitoring and issue reporting

Maintainer side:
- Release watcher: check each tool's stable releases (GitHub releases, npm). Ignore pre-releases.
- Canary: on a new stable release, run one short scripted session in that version, then the reviewer, and compare against expected numbers. Runs on the maintainer's machine; a CI variant needs API keys and is optional.
- CI runs each tool's manifest validator on every commit (`claude plugin validate --strict`, and the others' equivalents where they exist).
- Fixes are batched weekly; breaking ones are released as soon as fixed.

User side:
- When the health table shows a broken or warned core metric, the report includes a pre-filled GitHub issue link. It contains: tool name and version, skill version, install route, the health table, and the `--probe` structure output. No content, ids or paths. The user sees the full text before submitting.

## 12. Release management

- Semantic versioning. Patch: adapter and recorder mapping fixes. Minor: features. Major: findings schema or CLI changes that break existing use.
- One version source (SKILL.md frontmatter). A tag-triggered workflow runs tests and validators, writes the version into every `plugin.json`, and creates the GitHub release from CHANGELOG.md.
- Old tool versions keep working: adapter variants are added, never replaced.
- Update nudge (offline): when the tool's version is newer than the skill's tested versions, the report says so and prints the update command for the detected install route:

| Installed under | Command shown |
|---|---|
| `~/.claude/plugins/cache/…` | `/plugin marketplace update`, then update the plugin |
| `~/.codex/plugins/cache/…` | `codex plugin marketplace upgrade` |
| `~/.cursor/plugins/…` | Updates automatically; restart Cursor |
| `~/.agents/skills` (Skills CLI lock file present) | `npx skills update` |

## 13. Privacy and security

- The recorder stores only the fields in §6. Redaction runs on every string before writing.
- Logs are local, mode 0600 in a 0700 folder, deleted after the retention period.
- Recording is off by default, visible (`--record status`, and the report says whether a window was recorded), and removable (`--remove-hooks`, uninstalling the plugin, `--record purge`).
- The script stays offline: no network modules. The issue link is a URL the user opens; nothing is sent automatically.

## 15. Open questions

1. Hook reliability: Cursor users report some hook events not firing until a restart. Do we detect a recording with missing events and fall back to the transcript automatically?
2. Cursor records no tokens anywhere. Is "tokens not measurable" acceptable for Cursor in cross-session review, or do we drop token findings there?
3. Plugin skill names may be namespaced (e.g. `workflow-reviewer:workflow-reviewer`). What do users type, per tool?
4. Does the Agent Plugins standard add hooks? If it does, the three vendor plugins could become one.
5. Retention default: 14 days enough for cross-session review, or 30?
